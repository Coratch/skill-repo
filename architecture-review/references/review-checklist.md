# Architecture Review Checklist

## 1. Problem And Scope

- 目标是否可验证：成功标准、完成条件、验收方式是否明确。
- 决策主体是否明确：谁使用、谁运维、谁承担失败后果。
- 非目标是否明确：哪些问题本次不解决，为什么。
- 约束是否明确：兼容、合规、成本、性能、时间、组织边界。

## 2. Responsibilities And Boundaries

- 每个模块是否有单一、清晰的职责。
- 控制层、执行层、数据层、工具层、配置层是否混淆。
- 通用工作流能力和特定业务能力是否被错误耦合。
- 平台级配置和用户级/租户级配置是否隔离。
- 权限边界是否与调用边界一致。

## 3. Existing Capabilities

- 系统是否已有类似流程、模块、配置、工具、schema、adapter、benchmark。
- 新方案是否复用已有能力，而不是绕开或重复建设。
- 如果不复用，理由是否成立：边界不匹配、contract 不稳定、性能/安全不满足、迁移成本过高。
- 既有能力是否需要扩展，还是应该保持只读/只消费。
- 计划是否明确列出哪些已有能力不在本次改造范围。

## 4. Runtime Flow

- 入口、编排、执行、持久化、回调、终态是否完整。
- 同步/异步边界是否清楚。
- 状态机是否有明确的初始态、中间态、成功态、失败态、取消态。
- 超时、重试、幂等、并发、去重、恢复是否有设计。
- 下游失败时是否能定位、隔离、降级、回滚。

## 5. Data And Contract

- 输入和输出对象是否稳定、可校验、可版本化。
- 枚举、字段语义、必填/可选、默认值是否明确。
- 自然语言输出是否被误当作系统 contract。
- 是否区分 raw output、parsed output、normalized output、persisted output。
- 是否有 schema validation、contract tests、golden cases。
- 字段新增是否确有必要；是否可用现有字段表达。

## 6. Configuration

- 公共配置、环境配置、用户级私有配置、密钥是否分层。
- 配置来源、优先级、注入时机、运行时可见性是否明确。
- 容器挂载、环境变量、文件路径是否可验证。
- 配置变更是否需要重启、重建镜像、重新部署。
- 密钥是否避免进入代码、日志、镜像、提交历史。

## 7. Observability

- 是否能从一个 request/task id 追踪全链路。
- 是否记录关键输入、结构化输出、状态迁移、错误原因。
- 日志是否能区分业务失败、工具失败、LLM 失败、基础设施失败。
- 指标是否覆盖延迟、成功率、失败类型、重试、资源消耗。
- 是否有可重放的运行会话或 artifact。

## 8. Security And Privacy

- 身份认证和授权是否在每个 trust boundary 处生效。
- 用户级数据、密钥、日志、临时文件是否隔离。
- 工具/MCP/Agent 是否只获得必要权限。
- 外部系统 token 是否有最小权限、轮换和失效机制。
- 错误输出是否泄露敏感信息。

## 9. Evolution And Migration

- 是否支持向后兼容和灰度发布。
- 是否有旧数据、旧配置、旧任务、旧输出的兼容策略。
- 是否有明确的 rollback path。
- 方案是否把短期验证代码误固化为长期架构。
- 新抽象是否减少真实复杂度，而不是制造新的中间层。

## 10. Testing

- 单测覆盖纯逻辑、schema、解析器、状态机。
- 集成测试覆盖真实边界：数据库、队列、文件、MCP、LLM、容器挂载。
- E2E/golden case 覆盖代表性工作流和失败流。
- Benchmark case 可复现、可重复、可解释，不依赖偶然外部状态。
- 失败断言是否验证“为什么失败”，而不仅是失败状态。

## 11. Decision Quality

- 是否比较过保持现状、最小改造、长期方案。
- 是否明确 trade-off，而不是只列优点。
- 是否列出适用边界和失败模式。
- 是否给出先验证什么、如何验证、何时停止的路径。
- 是否能被未来维护者理解和复盘。
